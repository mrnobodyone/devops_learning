# ADR 0001: Vagrant + Ansible + k3s для локального стенда

## Контекст

Нужен воспроизводимый Kubernetes-стенд для обучения и демонстрации навыков.
Ограничения: один ПК (Windows 11, 16 ГБ RAM).
Стенд должен создаваться и удаляться одной командой.

## Рассмотренные варианты

| Вариант                         | Плюсы                              | Минусы                                       |
|---------------------------------|------------------------------------|----------------------------------------------|
| Облако (Terraform)              | ближе к проду                      | стоит денег                                  |
| kind / minikube                 | быстро, мало ресурсов              | нет настоящих ВМ, нет работы с Linux и SSH   |
| kubeadm на ВМ                   | максимально близко к проду         | тяжелее по ресурсам и по времени настройки   |
| **Vagrant + Ansible + k3s**     | настоящие ВМ, лёгкий Kubernetes    | k3s отличается от kubeadm в деталях          |

## Решение

- **Vagrant + VirtualBox** создают 4 ВМ (bastion, master, 2 worker) из кода.
- **Ansible** настраивает ВМ и ставит кластер. Запускается с bastion, а не с Windows: так не нужны WSL-специфичные пути, а управляющий узел воспроизводим вместе со стендом.
- **k3s** вместо kubeadm: нормально работает на 2 ГБ RAM на узел.
- Закрепляются версии: образ ВМ (box) и k3s, чтобы стенд собирался одинаково.
- Общая папка Vagrant отключена. На Windows у неё права 777, из-за чего SSH не принимает ключи оттуда, а Ansible игнорирует `ansible.cfg`.

## Последствия

- Нужен VirtualBox, и при включённом WSL2 он работает медленнее (режим поверх Hyper-V). Увеличен `boot_timeout`.
- Репозиторий должен лежать на диске Windows, иначе `vagrant.exe` из WSL не работает.
- Код на bastion берётся из GitHub (`git pull`), поэтому перед `up` изменения нужно коммитить и пушить.
- Опыт kubeadm остаётся за рамками проекта (k3s скрывает часть настройки control plane).
