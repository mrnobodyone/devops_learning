# ADR 0003: Terraform для загрузки платформы, GitOps для приложений

## Контекст

После сборки кластера (ADR 0001) нужно, чтобы платформенные компоненты (cert-manager, ArgoCD) тоже ставились из кода, и весь стенд поднимался командой `./scripts/up.sh` без ручных действий.

Одновременно приложение должно доставляться по GitOps: Git является источником истины, ArgoCD сам синхронизирует кластер с репозиторием `gitops-config`.

Нужно было определить границу между тем, что делает Terraform, и тем, что делает ArgoCD, а также выбрать способ создавать объекты на основе CRD (ClusterIssuer, Certificate, Application).

## Решения

### 1. Разделение ответственности

- **Terraform** ставит только то, что нужно для запуска GitOps: cert-manager, CA с ClusterIssuer'ами, ArgoCD и корневое приложение.
- **ArgoCD** управляет всем остальным. Корневое приложение (паттерн app-of-apps) указывает на каталог `argocd/` в `gitops-config` и подхватывает `shortener-dev` и `shortener-prod`.
- Terraform ничего не знает про окружения и версии приложения.
- Код Terraform лежит в репозитории платформы (`devops_learning`), а не в `gitops-config`. Иначе загрузчик оказался бы в репозитории, за которым следит ArgoCD, то есть система управляла бы собственной установкой.

### 2. Объекты на основе CRD через `helm_release` с локальными чартами

Рассмотренные варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| `kubernetes_manifest` (hashicorp) | официальный провайдер | на `plan` требует, чтобы CRD уже существовали, первый `apply` на чистом кластере падает |
| `kubectl_manifest` (alekc/kubectl) | CRD проверяются при применении | community-провайдер, не официальный; `plan` постоянно показывает изменение у `Application` из-за полей, которые добавляет ArgoCD |
| **`helm_release` с локальными чартами** | один официальный провайдер, нет проблем с CRD на `plan`, нет постоянного diff | манифесты оформлены как мини-чарты, ресурсы принадлежат релизам Helm |
| Issuers через ArgoCD | максимально GitOps | зависимость порядка (sync waves), сложнее начальная загрузка |

Выбран третий вариант: каталоги `terraform/charts/platform-issuers` и `terraform/charts/platform-root`. Порядок обеспечивают `depends_on` и `wait = true`.

### 3. Состояние и версии

- State локальный, на bastion. Он исчезает вместе со стендом, и это допустимо: кластер тоже создаётся заново. Для командной работы нужен remote backend.
- Версии чартов cert-manager и ArgoCD закреплены в `terraform.tfvars`.
- Версия провайдера `hashicorp/helm` закреплена в `.terraform.lock.hcl`, который лежит в репозитории. Мажорная версия не повышается без чтения upgrade guide: в 3.x изменился синтаксис блока `kubernetes`.
- `.terraform/` и `*.tfstate` исключены из Git.

### 4. Ручное одобрение прода

Приложение `shortener-prod` создано без `automated` в `syncPolicy`. ArgoCD показывает `OutOfSync`, а выкатка происходит только по ручному Sync.

## Последствия

- Весь стенд собирается одной командой: Vagrant, Ansible, затем `make bootstrap` (Terraform), затем ArgoCD подтягивает приложения.
- Повторный `terraform plan` не показывает изменений.
- Возможна гонка с webhook cert-manager: первый `apply` может упасть на issuers с ошибкой `failed calling webhook`. Повторный запуск проходит. При необходимости добавляется `time_sleep` между cert-manager и issuers.
- CA создаётся заново при каждом пересоздании стенда, поэтому сертификат в доверенных корневых Windows нужно обновлять.
- Для объектов, которыми управляет Helm, нельзя вносить правки руками через `kubectl`: следующий `apply` их перезапишет.
- Из-за локального state стенд нельзя безопасно разделять между несколькими людьми.
